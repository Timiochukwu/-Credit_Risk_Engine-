## Why Database Migrations Matter

**Problems Without Migrations:**
- Manual SQL changes are error-prone
- No version control for database schema
- Difficult to sync schema across environments
- Risky production deployments
- No rollback strategy

**Migration Benefits:**
- Version-controlled schema changes
- Automated, repeatable deployments
- Easy rollbacks
- Safe production updates

---

## Key Migration Patterns

### Zero-Downtime Migrations

**Expand-Contract Pattern:**
```
1. EXPAND: Add new column (nullable)
2. DEPLOY: Update code to write to both old and new
3. MIGRATE: Copy data from old to new column
4. DEPLOY: Update code to read from new column only
5. CONTRACT: Remove old column
```

### Migration Types

1. **Additive**: Add columns/tables (safe)
2. **Modificative**: Change columns (risky)
3. **Subtractive**: Remove columns/tables (dangerous)
4. **Data**: Transform data (slow)

## File 3: Safe Migration Examples

**File:** `alembic/versions/001_add_risk_score.py`

```python
"""Add risk_score column (zero-downtime)

Revision ID: 001
"""
from alembic import op
import sqlalchemy as sa


def upgrade():
    # Step 1: Add column as nullable
    op.add_column(
        'loan_applications',
        sa.Column('risk_score', sa.Float(), nullable=True)
    )

    # Step 2: Add index for performance
    op.create_index(
        'idx_risk_score',
        'loan_applications',
        ['risk_score']
    )


def downgrade():
    op.drop_index('idx_risk_score', table_name='loan_applications')
    op.drop_column('loan_applications', 'risk_score')
```

**File:** `alembic/versions/002_migrate_risk_data.py`

```python
"""Migrate risk score data

Revision ID: 002
"""
from alembic import op
from sqlalchemy.orm import Session
from sqlalchemy import text


def upgrade():
    # Get database session
    bind = op.get_bind()
    session = Session(bind=bind)

    # Batch update risk scores
    # (In production, do this in smaller batches)
    session.execute(
        text("""
            UPDATE loan_applications
            SET risk_score = (
                CASE
                    WHEN default = true THEN 0.8
                    ELSE 0.2
                END
            )
            WHERE risk_score IS NULL
        """)
    )

    session.commit()


def downgrade():
    bind = op.get_bind()
    session = Session(bind=bind)

    session.execute(
        text("UPDATE loan_applications SET risk_score = NULL")
    )

    session.commit()
```

## File 4: Migration CI/CD Integration

**File:** `.github/workflows/migrations.yml`

```yaml
name: Database Migrations

on:
  pull_request:
    paths:
      - 'alembic/versions/**'
      - 'src/models/**'

jobs:
  check-migrations:
    name: Validate Migrations
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:14
        env:
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.9'

      - name: Install dependencies
        run: |
          pip install alembic sqlalchemy psycopg2-binary

      - name: Test migrations (upgrade)
        env:
          DATABASE_URL: postgresql://postgres:testpass@localhost/testdb
        run: |
          alembic upgrade head
          echo "✓ Migrations applied successfully"

      - name: Test migrations (downgrade)
        env:
          DATABASE_URL: postgresql://postgres:testpass@localhost/testdb
        run: |
          alembic downgrade -1
          echo "✓ Rollback successful"

      - name: Check for conflicts
        run: |
          # Check if multiple heads exist
          HEADS=$(alembic heads | wc -l)
          if [ "$HEADS" -gt 1 ]; then
            echo "❌ Multiple migration heads detected"
            alembic heads
            exit 1
          fi
```

## File 5: Production Migration Workflow

**File:** `scripts/migrate-production.sh`

```bash
#!/bin/bash
# Safe production migration script

set -e

echo "========================================="
echo "  Production Migration"
echo "========================================="

# Configuration
DB_HOST="${PROD_DB_HOST}"
DB_NAME="${PROD_DB_NAME}"
DB_USER="${PROD_DB_USER}"

# Step 1: Backup database
echo "[1/5] Creating database backup..."
pg_dump -h $DB_HOST -U $DB_USER $DB_NAME | \
  gzip > backups/pre-migration-$(date +%Y%m%d_%H%M%S).sql.gz

# Step 2: Check current revision
echo "[2/5] Checking current migration state..."
CURRENT=$(alembic current | grep -oP '(?<=\(head\), )[a-z0-9]+')
echo "Current revision: $CURRENT"

# Step 3: Show pending migrations
echo "[3/5] Pending migrations:"
alembic upgrade head --sql | head -20

# Step 4: Confirm
read -p "Apply migrations? (yes/no): " CONFIRM
if [ "$CONFIRM" != "yes" ]; then
  echo "Migration cancelled"
  exit 0
fi

# Step 5: Apply migrations
echo "[4/5] Applying migrations..."
alembic upgrade head

# Step 6: Verify
echo "[5/5] Verifying..."
alembic current

echo "✓ Migration complete!"
```

```python
"""Test database migrations"""
import pytest
from alembic import command
from alembic.config import Config


def test_migrations_upgrade_downgrade(test_db):
    """Test that migrations can upgrade and downgrade"""
    alembic_cfg = Config("alembic.ini")

    # Upgrade to head
    command.upgrade(alembic_cfg, "head")

    # Downgrade one revision
    command.downgrade(alembic_cfg, "-1")

    # Upgrade back
    command.upgrade(alembic_cfg, "head")


def test_no_migration_conflicts():
    """Test that there are no migration branch conflicts"""
    alembic_cfg = Config("alembic.ini")

    # Should only have one head
    heads = command.heads(alembic_cfg)
    assert len(heads) == 1, "Multiple migration heads detected"
```

## Best Practices

### DO:
- ✅ Always make columns nullable first
- ✅ Add indexes concurrently in PostgreSQL
- ✅ Batch large data migrations
- ✅ Test migrations on staging first
- ✅ Backup before migrations
- ✅ Write rollback procedures

### DON'T:
- ❌ Drop columns immediately
- ❌ Add non-nullable columns without defaults
- ❌ Run long transactions in migrations
- ❌ Skip testing rollbacks
- ❌ Modify migrations after release

## Common Migration Patterns

### Add Column (Zero-Downtime)

```python
# Migration 1: Add nullable column
op.add_column('users', Column('email_verified', Boolean(), nullable=True))

# Migration 2: Backfill data
UPDATE users SET email_verified = false WHERE email_verified IS NULL

# Migration 3: Make non-nullable
op.alter_column('users', 'email_verified', nullable=False)
```

### Rename Column

```python
# Migration 1: Add new column
op.add_column('users', Column('full_name', String(200), nullable=True))

# Migration 2: Copy data
UPDATE users SET full_name = name

# Migration 3: Drop old column (after code updated)
op.drop_column('users', 'name')
```

## Key Takeaways

- **Plan Migrations**: Think through each step
- **Zero Downtime**: Use expand-contract pattern
- **Test Rollbacks**: Every migration must be reversible
- **Backup First**: Always backup before migrating
- **Batch Operations**: Large data migrations in chunks
- **Monitor Closely**: Watch database during migrations
