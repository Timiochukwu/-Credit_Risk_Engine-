# Day 035: Multi-Environment Setup

**Estimated time**: 2 hours

## What You'll Build Today

Today you'll set up a complete multi-environment infrastructure for your Credit Risk Engine. You'll configure separate dev, staging, and production environments with GitOps, manage environment-specific configurations, secure secrets, and implement a promotion workflow.

## Why Multiple Environments?

**Problem**: Deploying directly to production means:
- No testing before customers see changes
- Configuration mistakes affect live users
- Can't test infrastructure changes safely
- Difficult to reproduce production issues

**Solution**: Multi-environment setup provides:
- **Development**: For active development and experimentation
- **Staging**: Production replica for testing before release
- **Production**: Live customer-facing environment

**Benefits**:
- **Safety**: Test changes before production
- **Isolation**: Environments don't affect each other
- **Reproducibility**: Debug issues in non-production
- **Compliance**: Meet audit/security requirements

## Part 1: Environment Strategy

### Step 1: Define Environments

**Development (dev)**:
- Purpose: Active development, experimentation
- Deployment: On every commit to `develop` branch
- Resources: Minimal (1 replica, small nodes)
- Database: Shared dev database
- Secrets: Development credentials (non-sensitive)
- Access: All developers

**Staging (staging)**:
- Purpose: Pre-production testing, QA
- Deployment: On every commit to `main` branch
- Resources: Production-like (scaled down)
- Database: Staging database (production data copy)
- Secrets: Staging credentials
- Access: Developers + QA team

**Production (prod)**:
- Purpose: Live customer traffic
- Deployment: Manual approval or tag-based
- Resources: Full production scale (3+ replicas, large nodes)
- Database: Production database
- Secrets: Production credentials (highly sensitive)
- Access: Limited (SRE team only)

### Step 2: Namespace Strategy

Create separate namespaces per environment:

```bash
# Create namespaces
kubectl create namespace credit-risk-dev
kubectl create namespace credit-risk-staging
kubectl create namespace credit-risk-prod

kubectl label namespace credit-risk-staging istio-injection=enabled
kubectl label namespace credit-risk-prod istio-injection=enabled

# Label for environment identification
kubectl label namespace credit-risk-dev environment=dev
kubectl label namespace credit-risk-staging environment=staging
kubectl label namespace credit-risk-prod environment=prod
```

## Part 3: GitOps with ArgoCD

## Part 4: Secrets Management

Never commit secrets to Git. Use Sealed Secrets or External Secrets Operator.

### Option A: Sealed Secrets (Recommended for Simple Cases)

#### Step 1: Install Sealed Secrets Controller

```bash
# Install Sealed Secrets controller
kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.24.0/controller.yaml

# Install kubeseal CLI
wget https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.24.0/kubeseal-0.24.0-linux-amd64.tar.gz
tar xfz kubeseal-0.24.0-linux-amd64.tar.gz
sudo install -m 755 kubeseal /usr/local/bin/kubeseal
```

#### Step 2: Create and Seal Secrets

```bash
# Create regular secret (DON'T commit this)
kubectl create secret generic postgresql-staging-secret \
  --from-literal=password=staging-db-password-123 \
  --namespace credit-risk-staging \
  --dry-run=client -o yaml > /tmp/secret.yaml

# Seal it (this CAN be committed to git)
kubeseal -f /tmp/secret.yaml -w k8s/secrets/postgresql-staging-sealed-secret.yaml

# Delete temporary file
rm /tmp/secret.yaml
```

**`k8s/secrets/postgresql-staging-sealed-secret.yaml`** (safe to commit):

```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: postgresql-staging-secret
  namespace: credit-risk-staging
spec:
  encryptedData:
    password: AgBxY3J5cHRlZF9kYXRhX2hlcmU...  # Encrypted, safe to commit
  template:
    metadata:
      name: postgresql-staging-secret
      namespace: credit-risk-staging
```

Apply:

```bash
kubectl apply -f k8s/secrets/postgresql-staging-sealed-secret.yaml

# Controller decrypts and creates the real Secret
kubectl get secret postgresql-staging-secret -n credit-risk-staging
```

## Part 6: Environment Promotion Workflow

### Step 1: Define Promotion Process

**Dev → Staging**:
1. Merge feature branch to `develop`
2. CI builds and tags image: `dev-<commit-sha>`
3. ArgoCD auto-syncs to dev namespace
4. QA tests in dev
5. Merge `develop` to `main`
6. CI tags image: `staging-<commit-sha>`
7. ArgoCD auto-syncs to staging namespace

**Staging → Production**:
1. QA approves staging
2. Create git tag: `v1.0.0`
3. CI tags image: `v1.0.0`
4. Update ArgoCD prod application to track `v1.0.0`
5. Manual sync in ArgoCD (or auto-sync if enabled)
6. Monitor production deployment

### Step 2: Update GitHub Actions for Multi-Environment

**`.github/workflows/deploy.yaml`**:

```yaml
name: Deploy

on:
  push:
    branches:
      - develop   # Auto-deploy to dev
      - main      # Auto-deploy to staging
    tags:
      - 'v*'      # Manual deploy to prod

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v2

    - name: Login to GitHub Container Registry
      uses: docker/login-action@v2
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}

    - name: Determine image tag
      id: tag
      run: |
        if [[ $GITHUB_REF == refs/tags/* ]]; then
          echo "tag=${GITHUB_REF#refs/tags/}" >> $GITHUB_OUTPUT
        elif [[ $GITHUB_REF == refs/heads/main ]]; then
          echo "tag=staging-${GITHUB_SHA::7}" >> $GITHUB_OUTPUT
        elif [[ $GITHUB_REF == refs/heads/develop ]]; then
          echo "tag=dev-${GITHUB_SHA::7}" >> $GITHUB_OUTPUT
        fi

    - name: Build and push
      uses: docker/build-push-action@v4
      with:
        context: .
        push: true
        tags: ghcr.io/${{ github.repository }}:${{ steps.tag.outputs.tag }}
        cache-from: type=gha
        cache-to: type=gha,mode=max

  update-argocd:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
    - name: Update ArgoCD application
      if: startsWith(github.ref, 'refs/tags/')
      run: |
        # Update prod application to new tag
        kubectl patch application credit-risk-prod \
          -n argocd \
          --type merge \
          -p '{"spec":{"source":{"targetRevision":"${{ steps.tag.outputs.tag }}"}}}'
```

### Step 3: Create Promotion Script

**`scripts/promote.sh`**:

```bash
#!/bin/bash

set -e

ENV=$1
VERSION=$2

if [ -z "$ENV" ] || [ -z "$VERSION" ]; then
  echo "Usage: ./promote.sh <staging|prod> <version>"
  exit 1
fi

if [ "$ENV" == "staging" ]; then
  echo "Promoting to staging: $VERSION"
  git checkout main
  git merge develop
  git tag "staging-$VERSION"
  git push origin main --tags
  echo "✅ Promoted to staging. ArgoCD will auto-sync."

elif [ "$ENV" == "prod" ]; then
  echo "Promoting to production: $VERSION"
  read -p "Are you sure? (yes/no): " confirm
  if [ "$confirm" != "yes" ]; then
    echo "Aborted."
    exit 1
  fi

  git tag "v$VERSION"
  git push origin --tags

  echo "✅ Tagged v$VERSION. Update ArgoCD prod application:"
  echo "   kubectl patch application credit-risk-prod -n argocd \\"
  echo "     --type merge -p '{\"spec\":{\"source\":{\"targetRevision\":\"v$VERSION\"}}}'"
  echo ""
  echo "   Then sync: argocd app sync credit-risk-prod"
fi
```

Usage:

```bash
chmod +x scripts/promote.sh

# Promote to staging
./scripts/promote.sh staging 1.1.0

# Promote to production
./scripts/promote.sh prod 1.1.0
```

## Best Practices

### 1. Use Environment Parity

Keep staging as close to production as possible:
- Same Kubernetes version
- Same Istio version
- Same database version
- Similar resource allocations

### 2. Automate Dev/Staging, Manual Prod

```yaml
# Dev/Staging: Auto-sync
syncPolicy:
  automated:
    prune: true
    selfHeal: true

# Prod: Manual sync
syncPolicy:
  automated:
    prune: false
    selfHeal: false
```

### 3. Version Everything

```yaml
# BAD: Using 'latest' in prod
image:
  tag: latest

# GOOD: Using specific version
image:
  tag: v1.0.0
```

### 4. Separate Secrets Per Environment

Don't reuse secrets across environments:
- `postgresql-dev-secret`
- `postgresql-staging-secret`
- `postgresql-prod-secret`

### 5. Monitor All Environments

```bash
# Check controller logs
kubectl logs -n kube-system deployment/sealed-secrets-controller

# Verify certificate
kubeseal --fetch-cert

# Re-seal with correct certificate
kubeseal --cert /path/to/cert.pem -f secret.yaml -w sealed-secret.yaml
```
