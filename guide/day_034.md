# Day 034: Service Mesh with Istio

**Estimated time**: 2 hours

## What You'll Build Today

Today you'll implement Istio service mesh for your Credit Risk Engine. You'll set up advanced traffic management, implement canary deployments, configure circuit breaking, enable mutual TLS, and gain deep observability into your microservices.

## Why Service Mesh?

**Problem**: As microservices grow, you need:
- **Traffic management**: Canary deployments, A/B testing, traffic splitting
- **Security**: mTLS between services, authentication, authorization
- **Observability**: Distributed tracing, metrics, service topology
- **Resilience**: Circuit breaking, retries, timeouts, fault injection

Without a service mesh, you must implement these in every service.

**Solution**: Service mesh provides:
- **Sidecar proxies**: Envoy proxy injected into each pod
- **Control plane**: Istio manages proxy configuration
- **Transparent**: No code changes needed
- **Centralized**: Configure once, apply to all services

**Benefits**:
- **Zero code changes**: Works with existing services
- **Centralized policy**: Traffic rules, security policies in one place
- **Deep observability**: Automatic tracing, metrics, logs
- **Advanced deployment**: Canary, blue-green, A/B testing

## Part 2: Traffic Management

### Step 1: Create Gateway

Gateway configures Istio ingress to accept external traffic.

**`k8s/istio/gateway.yaml`**:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: credit-risk-gateway
  namespace: credit-risk
spec:
  selector:
    istio: ingressgateway  # Use Istio's ingress gateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "credit-risk.example.com"  # Your domain
    - "*"  # Accept all hosts (for testing)
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: credit-risk-tls  # Secret with TLS cert
    hosts:
    - "credit-risk.example.com"
```

Apply:

```bash
kubectl apply -f k8s/istio/gateway.yaml
```

### Step 2: Create VirtualService

VirtualService routes traffic from Gateway to your service.

**`k8s/istio/virtualservice.yaml`**:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: credit-risk-api
  namespace: credit-risk
spec:
  hosts:
  - "credit-risk.example.com"
  - "*"  # For testing
  gateways:
  - credit-risk-gateway
  http:
  - match:
    - uri:
        prefix: "/api/v1"
    route:
    - destination:
        host: credit-risk-engine  # Service name
        port:
          number: 8000
    timeout: 30s
    retries:
      attempts: 3
      perTryTimeout: 10s
      retryOn: 5xx,reset,connect-failure,refused-stream
  - match:
    - uri:
        prefix: "/health"
    route:
    - destination:
        host: credit-risk-engine
        port:
          number: 8000
    timeout: 5s
```

Apply:

```bash
kubectl apply -f k8s/istio/virtualservice.yaml
```

### Step 3: Create DestinationRule

DestinationRule defines subsets (versions) of a service.

**`k8s/istio/destinationrule.yaml`**:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: credit-risk-engine
  namespace: credit-risk
spec:
  host: credit-risk-engine
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST  # Load balancing algorithm
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 50
        http2MaxRequests: 100
        maxRequestsPerConnection: 2
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

Apply:

```bash
kubectl apply -f k8s/istio/destinationrule.yaml
```

### Step 4: Configure Traffic Splitting

Update VirtualService to split traffic 90/10 (90% to v1, 10% to v2):

**`k8s/istio/virtualservice-canary.yaml`**:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: credit-risk-api
  namespace: credit-risk
spec:
  hosts:
  - "credit-risk.example.com"
  - "*"
  gateways:
  - credit-risk-gateway
  http:
  - match:
    - uri:
        prefix: "/api/v1"
    route:
    - destination:
        host: credit-risk-engine
        subset: v1
        port:
          number: 8000
      weight: 90  # 90% to v1
    - destination:
        host: credit-risk-engine
        subset: v2
        port:
          number: 8000
      weight: 10  # 10% to v2
    timeout: 30s
    retries:
      attempts: 3
      perTryTimeout: 10s
```

Apply:

```bash
kubectl apply -f k8s/istio/virtualservice-canary.yaml
```

## Part 4: Circuit Breaking

Prevent cascading failures with circuit breakers.

### Step 1: Configure Circuit Breaking

Already configured in DestinationRule (from Part 3):

```yaml
spec:
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100        # Max TCP connections
      http:
        http1MaxPendingRequests: 50   # Max pending requests
        http2MaxRequests: 100          # Max requests
        maxRequestsPerConnection: 2    # Requests per connection
    outlierDetection:
      consecutiveErrors: 5          # Errors before ejection
      interval: 30s                 # Detection interval
      baseEjectionTime: 30s         # Minimum ejection duration
      maxEjectionPercent: 50        # Max % of hosts to eject
```

This means:
- If a pod has 5 consecutive errors, it's ejected from pool for 30s
- Max 50% of pods can be ejected (maintain availability)
- Connection limits prevent overload

### Step 2: Test Circuit Breaker

Create a load test that exceeds limits:

**`scripts/circuit_breaker_test.sh`**:

```bash
#!/bin/bash

GATEWAY_URL=$(kubectl get svc istio-ingressgateway -n istio-system -o jsonpath='{.status.loadBalancer.ingress[0].ip}')

echo "Testing circuit breaker with $GATEWAY_URL"

# Generate load that exceeds connection pool
for i in {1..200}; do
  (
    curl -X POST http://$GATEWAY_URL/api/v1/predict \
      -H "Content-Type: application/json" \
      -d '{
        "loan_amount": 50000,
        "age": 35,
        "employment_length": 5,
        "income": 75000,
        "debt_to_income": 0.35,
        "credit_score": 720,
        "num_credit_lines": 8,
        "loan_purpose": "debt_consolidation",
        "state_code": "LA"
      }' \
      -w "HTTP %{http_code}\n" \
      -o /dev/null
  ) &
done

wait

echo "Load test complete"
```

Run and check for 503 (circuit breaker triggered):

```bash
chmod +x scripts/circuit_breaker_test.sh
./scripts/circuit_breaker_test.sh

# Should see some 503 Service Unavailable responses
```

## Part 5: Mutual TLS (mTLS)

Encrypt all service-to-service communication.

### Step 1: Enable Strict mTLS

**`k8s/istio/peer-authentication.yaml`**:

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: credit-risk
spec:
  mtls:
    mode: STRICT  # Require mTLS for all services
```

Apply:

```bash
kubectl apply -f k8s/istio/peer-authentication.yaml
```

This automatically:
- Generates certificates for each pod
- Encrypts all traffic between pods
- Rotates certificates automatically

## Part 8: Best Practices

### 1. Start with Permissive mTLS, Then Strict

```yaml
# Phase 1: Permissive (allows both mTLS and plaintext)
spec:
  mtls:
    mode: PERMISSIVE

# Phase 2: After verifying all services work, switch to STRICT
spec:
  mtls:
    mode: STRICT
```

### 2. Set Sensible Timeouts and Retries

```yaml
http:
- route:
  - destination:
      host: credit-risk-engine
  timeout: 30s  # Overall timeout
  retries:
    attempts: 3
    perTryTimeout: 10s  # Per-attempt timeout
    retryOn: 5xx,reset,connect-failure
```

### 3. Use Circuit Breakers for External Services

```yaml
spec:
  host: external-api.example.com
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 10
      http:
        http1MaxPendingRequests: 5
        maxRequestsPerConnection: 1
    outlierDetection:
      consecutiveErrors: 3
      interval: 10s
      baseEjectionTime: 60s
```

### 4. Monitor Control Plane

```bash
# Check istiod resource usage
kubectl top pod -n istio-system

# Check proxy sync status
istioctl proxy-status

# Validate configuration
istioctl analyze -n credit-risk
```

### 5. Use Namespace-Level Policies

Apply policies at namespace level for consistency:

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: credit-risk  # Namespace-wide policy
spec:
  mtls:
    mode: STRICT
```
